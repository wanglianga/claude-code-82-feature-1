# 🏊 蓝鲸社区泳池 · 预约入场与水质救生巡查协同平台

一个围绕「同一场次」把**居民端与现场端**拉到同一份实时事实上的一体化页面：居民预约 → 前台核验 → 救生巡查/水质监测 → 保洁维修工单 → 运营指挥/闭池联动，六类角色通过 TanStack Query 4 秒轮询共享状态，闭池时退费、补偿券、水质复测、救生清场与居民通知一次性联动，杜绝两端状态不一致。

技术栈：**React 18 + TypeScript + TanStack Query + Vite**（前端），**Express + TypeScript**（后端/静态托管），JSON 原子落盘（无需外部数据库，零依赖一键启动），多阶段 Docker 镜像、非 root 运行、内置 HEALTHCHECK。

## 原始需求（本轮新增：培训机构包场与居民公益时段冲突协调）

> 增加培训机构包场与居民公益时段冲突协调。培训机构或商业团体申请包场时，页面先按日期、时段、泳道、泳区、更衣淋浴容量、储物柜数量、救生员排班和已预约居民列出冲突范围，标出老人晨泳、亲子时段、居民公益时段、教练课和会员储值用户。平台不能直接覆盖居民预约，需核验机构资质、教练和救生员配置、保险、人数、年龄结构、是否含儿童、独立出入口和更衣需求；涉及儿童的，按儿童离陪规则核验陪同人，不能因为包场就放宽。运营可拆分泳道、缩短包场、限制人数、增派救生员、暂停部分非公益泳道或提供改约补偿券；若居民不同意改约，保留原预约并压缩包场范围。包场费用按泳道、时段、救生员加班、储物柜和淋浴区占用拆分，进入机构账单；居民公益时段被压缩的，退费或补偿券同步居民端，不能只在内部记一笔。包场当天，前台核验机构名单、访客身份和保险，救生员按包场人数重新站位，保洁和维修确认地面、淋浴、储物柜和消毒安排；出现超人数、超时、占用公益泳道、儿童无人陪同或机构私自加人，现场可暂停包场并通知社区运营。包场结束后先清场、清储物柜、水质复测、设备复位和救生巡查确认，再恢复居民预约；未复测或未清场不得开放下一场。机构信用记录超时、超人数、投诉和整改情况，频繁违规的限制后续包场或要求增加救生员和押金。所有冲突协调、居民改约、补偿、机构确认和恢复开放结果进入该场次记录，供后续排期和投诉追溯。

### 本轮实现要点（对应原始需求逐条落地）

1. **申请前冲突预览**（`POST /api/rentals/preview`）：按日期/时段、泳道、泳区、泳区容量、更衣淋浴容量、储物柜数量、救生员排班、已预约居民列出冲突范围；居民逐笔打标签——**老人晨泳、亲子时段、居民公益、教练课、会员储值、含儿童、深水证**。
2. **平台不覆盖居民预约**：批准前所有在批准范围内的居民必须逐笔完成改约/退费/补偿/保留处置；居民"不同意改约"则保留原预约，系统强制运营**压缩包场范围**（拆道/换泳区），否则拒绝批准；**居民公益时段禁止整区商业包场**，只能拆分配套非公益泳道。
3. **机构核验**：办学/营业执照、教练资质配置、救生员资质配置、保险（单号+有效期，过期拒批）、独立出入口、独立更衣淋浴六项**逐项核验**；人数/年龄结构/是否含儿童登记。
4. **儿童离陪规则不放宽**：6 岁以下幼儿 1:1、其余未成年人 1:3 配备成人陪同（教练/救生员不计入陪同）；申请与批准两道关口都校验，人数不足直接拒绝。
5. **运营协调措施**：拆分泳道（多道逐道加锁）、缩短时段、限制人数/儿童数、增派救生员、暂停部分非公益泳道（公益泳道不暂停）、提供改约补偿券、追加押金。
6. **居民改约征询闭环**：运营逐人发起征询 → 居民端在"我的预约"收到征询卡选择同意/不同意 → 运营可一键落单同意者，或逐笔改约/原路退费/退费+补偿券；**公益/居民时段被压缩的退费与补偿券真实到账居民端（钱包/补偿券/逐人通知），不是内部记一笔**。
7. **费用拆分进机构账单**：按**泳道（道·小时）/救生员加班/储物柜/淋浴区占用/押金**分项核算，对公或机构储值支付，进入机构账单，运营可查。
8. **包场当天六岗核验**：前台核验机构名单/访客身份/保险，救生员按包场人数重新站位（自动生成机动岗），保洁确认地面/淋浴/储物柜/消毒，维修确认设备与消毒安排（含角色 RBAC）。
9. **现场违规可暂停**：超人数、超时、占用公益泳道、儿童无人陪同、私自加人、投诉成立 → 登记即**自动立案协同事件、扣机构信用、可一键现场暂停并通知社区运营**；整改通过后恢复，信用部分回补。
10. **清场五项门禁**：包场结束后须依次完成**清场、清储物柜、水质复测达标（须晚于结束时间的达标读数）、设备复位、救生巡查确认**，缺一不可恢复居民预约/开放下一场；恢复时逐道释放锁区。
11. **机构信用与限制**：信用分（初始 100，违规扣分、整改回补）、押金、强制增派救生员；信用低于 60 或运营可限制后续包场，被限制机构申请直接 403；可追加/扣抵押金。
12. **全程场次记录**：申请、资质核验、改约征询与答复、逐人处置、补偿、机构确认、批准、当天六岗、违规与整改、清场五项、恢复开放全部写入该场次**审计时间线**，供后续排期与投诉追溯。

## 原始需求（本轮新增：抽筋救援记录）

> 增加抽筋救援记录。泳客在泳道抽筋后，救生员记录发现时间、救援方式、上岸处理、是否联系家属和是否建议就医。救援记录会影响该场次复盘和救生员站位调整。救援结束后，救生员换岗、泳道临停和水面秩序恢复都要确认。站位调整后，下一场救生巡查会提醒救生员重点关注同一泳道。复盘结果会进入救生员培训和排班。

### 迭代修复：多次站位调整与后续场次重点关注的版本错配

> 修复抽筋救援多次站位调整与后续场次重点关注版本错配：在 server/cramp.ts 中让每次调整按版本同步所有尚未开始的目标场，下一场提醒展示最新策略；已确认的提醒遇到新调整必须重新待确认，同时保留每次调整和历次确认的审计关系，不得改写已结束场次。验收：第二次调整后未确认下午场显示第二次策略；已确认后再调整重新待确认且历史确认可查；早于事发和已结束场次不变，复盘培训链路正常。

## 抽筋救援记录（发现 → 临停立案 → 三项收尾确认 → 站位调整 → 下一场关注 → 复盘培训排班）

救生员在「🆘 抽筋救援」页登记泳客在泳道抽筋的救援记录（`server/cramp.ts` + `src/components/cramp.tsx`），整条链路围绕同一场次联动：

1. **登记救援**：发现时间、泳区/泳道、抽筋部位、救援方式（岸上伸援/下水搀扶/游泳拖带/脊柱板/AED 急救）、上岸处理、被救泳客描述、是否联系家属、是否建议就医。
2. **自动联动**：① 该泳道**临时关闭**（写入场次 `suspendedLanes`），居民预约与前台核验在**泳道级**被拦截（同泳区其他泳道不受影响），居民侧只见“现场处置，泳道临时关闭”脱敏文案；② 自动立案/挂接「泳客抽筋」跨角色协同事件（前台取 AED/联系陪同人、保洁疏散围观、运营跟进送医）；③ 向前台/救生/保洁/运营推送通告（建议就医时为紧急级）。
3. **救援结束三项收尾确认**（缺一不可，全部完成才能复盘）：
   - **救生员换岗确认**：选名册内接班人后**真实联动站位**——施救救生员当前在岗记录结束、接班人自动上同一站位（复用 `guardDuties`，带 `crampRescueId` 痕迹）；接班人若在其他站位在岗会被拒绝，须先交岗；也支持线下换岗说明；
   - **泳道临停解除确认**：移除临停、该泳道恢复预约/放行，并推送恢复通告；
   - **水面秩序恢复确认**：围观疏散、游进秩序正常。
4. **站位调整（多版本策略，按版本同步所有未开始场次）**：记录调整内容（加派机动、重点瞭望、热身广播等）即生成一个新版本（`CrampPostAdjustment.version` 从 1 递增），可勾选同步；同步时**只写严格晚于事发场次且尚未开始的目标场**（早于事发、进行中、已结束场次一律不改写）：
   - 目标场首次出现 → 新建当前版关注提醒；已有同泳道提醒 → 把旧版（连同该版本当时的确认人/时间）归档进 `history`，再把提醒刷新为**最新版策略并清空确认状态**，救生员必须按新版**重新确认**；
   - 下一场救生员实时看板顶部始终显示“🛟 本场重点关注 X 号道 · 第 N 版策略”，未确认时按钮提示“新版本，需重新确认”；展开「历次策略与确认留痕」可查每一版的策略文案、制定人与该版确认情况（已确认后被替换也保留确认痕迹）；
   - 不勾选向下同步时，仅在救援记录上留痕新版本，不改写任何场次的既有提醒。
5. **本场复盘 → 培训与排班**：三项确认齐备后由运营在「🆘 救援复盘培训」页组织复盘（未完成确认时复盘被 409 拒绝，复盘不可重复），生成 `GuardTrainingItem`（培训要点、参训救生员、是否进入排班/带教备注），救生员在本人工作台看到培训项并登记参训完成。
6. **多角色可见性（服务端裁剪）**：救生/运营/前台见救援全量；前台核验台顶部有现场救援条（家属/就医/临停状态），但不见救生内部关注泳道；保洁/维修仅经抽筋事件见到关联救援；**居民快照不含任何救援记录、培训项与关注泳道**，临停原因脱敏。
7. **运营指挥台时间线**自动串联：发现救援 → 三项收尾确认 → 站位调整 → 复盘生成培训/排班。种子数据含一条早场老人晨泳已复盘救援 `CR-2059`，其站位调整已带入「当前场次」浅水 2 号道关注提醒与一条培训项，登录即体验“下一场重点关注”。

## 原始需求

> 设计社区泳池预约入场与水质救生巡查页面，可使用 React、TypeScript 和 TanStack Query。居民预约泳道或亲子时段时，页面记录会员身份、年龄、健康承诺、是否带儿童、游泳水平和入场时段。前台核验预约、健康码或体检证明、儿童陪同人和储物柜，救生员端看到当前泳道人数、儿童区人数、深水区权限、水温、余氯、浊度和设备状态。运营人员巡查时，需要记录救生员站位、泳客违规跳水、儿童离开陪同人、地面湿滑、淋浴区拥堵和水质检测。若水质异常、雷雨临近、泳客抽筋、儿童走失、储物柜纠纷或预约超额，页面要让前台、救生员、保洁、维修和社区运营围绕同一场次处理。闭池或恢复开放时，预约退费、补偿券、水质复测、救生巡查和居民通知一起更新，避免居民端和现场端状态不一致。页面还要覆盖会员储值、教练课、团体预约、泳池消毒、救生员换岗和居民投诉。不同泳区的容量、风险和开放规则不同，运营人员要能看到一个场次从预约、入场、巡查到清场的完整状态。泳池还要处理外来访客、游泳培训机构包场、老人晨泳和暑期儿童高峰，运营人员需要在同一页面上看到商业预约和居民公益时段之间的冲突。

## 一键启动（Docker Compose）

```bash
cp .env.example .env        # 可按需修改 CC_PUBLISH_PORT（宿主发布端口，默认 3082）
docker compose up -d --build
```

- 容器内服务监听 `4000`，**仅应用端口发布到宿主**：`${CC_PUBLISH_PORT}:4000`；无数据库/缓存端口暴露。
- 数据保存在命名卷 `pool-data`（`/data/pool-db.json`，原子写）。首次启动自动播种当日演示数据（场次时间相对当前时刻生成，打开即有一个「进行中」的场次）。
- 取实际映射端口并访问（不要硬编码 3000/3082，避免并行任务冲突）：

```bash
docker compose port app 4000          # 例如 0.0.0.0:3082
# 浏览器打开 http://host.docker.internal:<端口>/
curl http://host.docker.internal:<端口>/api/health   # {"status":"healthy",...}
```

健康检查：镜像内置 `HEALTHCHECK`（wget 探活 `/api/health`），`docker compose ps` 可见 `(healthy)`。

停止并释放资源：

```bash
docker compose down          # 保留数据卷
docker compose down -v       # 同时清空演示数据（下次启动重新播种）
```

### 本地开发（可选）

```bash
npm install
npm run dev:server    # 终端 1：Express API :4000
npm run dev:client    # 终端 2：Vite :5173（/api 代理到 4000）
npm run build          # 类型检查 + 前后端产物

## 角色化数据视图（服务端脱敏，非前端筛选）

`GET /api/state` 不再下发全库快照，而是由 `server/views.ts` 依据**会话用户**在服务端裁剪，前端 TanStack Query 拿到的本身就是最小可见集合：

| 角色 | 可见范围 |
| --- | --- |
| 居民 | 仅**本人**预约、本人钱包流水、本人投诉、广播/个人通知；泳区只给人数/容量聚合；人员目录为空；锁区标题泛化（「该区域已被包场」，不见机构名与联系人）；课程学员名单只保留本人 id；撞锁区报错不回显机构名、他人预约码 |
| 前台 | 全部预约 + 有预约泳客的最小人员卡片（姓名/电话/会员等级/深水证，**无余额/补偿券**）；无钱包流水、无设备清单 |
| 救生员 | 看板聚合（各泳区在池人数、儿童数、深水证持有数、占用率）、水质、设备、排班、巡查、事件；无逐笔预约、无钱包、人员目录仅救生员且无电话 |
| 保洁 | 仅保洁岗工单、分派给保洁的巡查、需要保洁参与的事件；无预约/钱包/设备/投诉 |
| 维修 | 仅维修岗工单（含消毒复测）、设备、水质、需要维修参与的事件；无预约/钱包/投诉 |
| 运营 | 全量业务视图（退费处置、投诉答复、冲突协调所必需），人员卡片同样不含密码 |

闭池联动后，受影响居民各自只能在自己的快照里看到**自己那笔**退费流水、补偿状态与逐人通知；`privacy-check.mjs` 对上述边界做了 **44 项断言**（含快照 JSON 中不得出现他人手机号/姓名/预约码/陪同人等字符串级检查）。抽筋救援同样按角色裁剪：居民快照不含任何救援记录、救生培训项与重点关注泳道，临停泳道仅显示脱敏文案“现场处置，泳道临时关闭”（`cramp-rescue-check.mjs` 另含字符串级隐私断言）。

## 水质异常处置（锁定时段 · 三种处置 · 分人群补偿 · 教练课顺延）

救生员/维修录入余氯不足或浊度超标的读数后，系统**自动限流**并锁定时段，运营在「闭池与恢复」页看到受影响泳区的**已入场人数、未入场预约、教练课人数与复测计划**，再三选一处置（均生成不可变 `ClosureRecord`，`disposition` 字段区分）：

| 处置方式 | 场次状态 | 范围 | 补偿口径 |
| --- | --- | --- | --- |
| 部分开放 `partial` | 仅受影响泳区锁定，其余正常核验/预约 | 勾选泳区 | 受影响泳区人群按下表；非受影响泳区完全不受影响 |
| 闭池 `closed` | 全场清场 | 全部泳区 | 撤全部在岗救生岗 + 清场清洁/消毒复测工单 |
| 延期 `postponed` | 当前场暂停 | 全部泳区 | 未入场预约与教练课**真实迁移**到目标场次（同事务生成可核验的 `booked` 新预约），费用保留不退款 |

**延期真实迁移（不产生只有通知的 postponed 死单）：**
- 同一事务内，在目标场次为每笔未入场预约/教练课预约生成一笔 `booked` 新预约，原预约置 `postponed` 并双向关联（`postponedBookingId` / `migratedFromBookingId` / `migratedClosureId`）；不退款、不二次扣款，目标场容量、前台待核验队列、救生在场统计自动纳入；
- **前置门禁**：目标场已闭池/部分开放，或任一泳区现有在池+待入+锁定+迁入超过容量时，整个延期请求被 409 拒绝，原预约、费用、通知与闭池档案保持不变，绝不留下无法核验的 postponed 订单；
- 已入场（人在现场）不迁移，按提前清场发安抚券；档案记录 `migratedBookingCount/migrationSummary`，居民端同时看到原单「顺延至下午场（新预约 B-xxxx）」与目标场的有效预约。

**受影响人群差异化补偿（按实际影响，逐人通知）：**
- **未入场**：按原支付渠道原路退款（储值退余额 / 券返原券 / 现金现场登记），可叠加额外补偿券；
- **已入场**（强制清场，服务已部分使用）：不退现金，发**安抚补偿券**；
- **教练课**（`kind=coaching` 或受影响泳区内的课程）：课程与学员预约顺延到后续场次、费用保留，**学员与机构账号分别收到顺延通知**；部分开放时无需全场清场，恢复门禁只需消毒复测工单（不含清场）。

档案新增 `disposition / affectedZoneIds / retestPlannedAt / postponeToSessionId / groupCounts（checked_in/not_checked_in/coaching）/ lessonPostponements`；场次新增 `affectedZoneIds / retestPlannedAt`；预约与课程状态新增「已顺延」并记录目标场次；救生看板对受影响泳区显示「暂停开放」红色锁定态。恢复门禁按处置方式区分：闭池/延期需清场清洁+消毒复测+必要达标水质，部分开放只需消毒复测+复测。


## 闭池处置档案（不可变快照，支持同场次多次闭池）

每次执行闭池都会生成一条独立的 `ClosureRecord`（`server/domain.ts`），**一经固化不再被当前场次状态覆盖**：

- **退款严格按原支付渠道分别处理，互不混记**：储值支付仅退回储值余额（产生一条钱包流水）；补偿券支付仅返还原券、**不产生任何金额流水**；现场支付不进储值，只登记「凭预约码到前台办理现场退款」结果；公益免费单无需退款。额外发放的补偿券与原券返还原分开统计（`originalVoucherReturnCount` vs `extraVoucherCount`）；档案按渠道汇总 `walletRefundTotal/Count`、`cashRefundTotal/Count`，通知按居民合并为一条并逐笔列明各渠道结论，不再统一宣称“已退回账户”；
- 档案逐字保存：闭池序号（第 N 轮）、原因分类与原文（雷雨/水质…）、闭池时间与操作人、是否要求复测、逐笔受影响预约的渠道退款/原券返还/额外补偿券/通知送达结果、撤哨人数、消毒复测与清场工单、关联事件；
- 退费钱包流水、补偿预约、逐人通知与工单均带 `closureId`，反向引用同一档案；居民通知标题带「第 N 轮」；
- **恢复开放只更新当前开放状态**（`poolStatus`、清空 `activeClosureId`），并仅回写本轮档案的 `reopenedAt/reopenedBy/retestReadingId`；历史档案的原因与处置结果保持不变；
- 场次恢复后允许再次闭池：场次 `closureIds` 累积全部档案，运营时间线与「闭池与恢复」底部按轮次展示，雷雨档案与水质档案互不覆盖；
- **恢复门禁以当前生效闭池档案为唯一依据**，三项齐备才放行：① 本轮联动生成的**清场清洁工单**（保洁）已完成；② 本轮**消毒复测工单**（维修）已完成；③ 水质原因闭池时存在晚于本轮闭池时间的**达标水质读数**。只录入合格水质而清场/消毒待办未完成时，恢复请求被 409 拒绝，场次状态、居民通知与退费补偿档案均不变化；
- 恢复瞬间把三项完成结果（工单人/完成时间/结论、复测读数、送达通知 id）固化到档案的 `reopenChecklist`/`reopenNotificationIds`，运营端与居民端看到同一份清场、复测和通知结果；
- 角色视图同步裁剪：运营看全量档案与逐人明细，居民只看到含本人的条目，救生/保洁/维修只见原因、状态与本岗工单，不见逐人退款金额。

| 泳道人数、儿童区人数、深水区权限、水温/余氯/浊度、设备状态 | 救生员「实时看板」：四泳区占用条、在场儿童、深水证持证比例、四项水质仪表、设备牌 |
| 救生员站位、违规跳水、儿童脱陪、地面湿滑、淋浴拥堵、水质检测 | 「救生巡查」六类问题 + 自动分派（湿滑/拥堵→保洁工单，水质→维修消毒工单）；「站位与换岗」记录上哨/接班 |
| 六种紧急情况围绕同场次协同 | 事件模板（`server/domain.ts`）按类型生成前台/救生/保洁/维修/运营各自处置清单，同屏进展时间线；保洁/维修事项自动转工单 |
| 闭池/恢复：退费+补偿券+复测+救生巡查+通知一起更新 | `changePoolStatus` 单次原子事务；恢复开放以本轮闭池档案为唯一门禁：清场清洁、消毒复测工单与必要的达标水质全部完成，核验结果回写同一档案 |
| 会员储值/教练课/团体/消毒/换岗/投诉 | 钱包充值与流水、教学道课程报名扣款、≥5 人团体、消毒工单、换岗交接、投诉答复闭环 |
| 泳区容量/风险/开放规则差异 | 4 个泳区独立容量与规则（深水区高风险凭证、亲子区一对一陪同、浅水区老人优先），锁区名额参与容量计算 |
| 场次 预约→入场→巡查→清场 完整状态 | 运营「场次指挥台」：生命周期步骤条 + 汇总指标 + 全量时间线 |
| 访客/机构包场/老人晨泳/暑期高峰 | 七类预约 `BookingKind`，访客票价、公益免费、晚高峰容量预警 |
| 商业预约 vs 居民公益冲突 | 基础锁区冲突检测（公益场/居民预约/锁区重叠/超容量四类标红）保留；**完整协调见下：包场申请→冲突预览→资质核验→居民改约→压缩范围→批准** |
| 培训机构包场与公益时段冲突协调 | **「⚖️ 包场冲突协调」页（`server/rental.ts` + `src/components/rental.tsx`）**：申请前按日期/时段/泳道/泳区/更衣淋浴/储物柜/救生排班/已预约居民列出冲突并给老人晨泳/亲子/公益/教练课/会员储值打标签；平台不覆盖居民，六项资质+教练救生+保险+独立出入口/更衣逐项核验，儿童按 1:1/1:3 离陪规则不放宽；拆道/缩短/限人/增派救生/暂停非公益道/补偿券；居民不同意即保留并压缩范围；费用按泳道/加班/储物柜/淋浴/押金拆分进机构账单；当天六岗核验、违规暂停立案扣信用、清场五项门禁后恢复；信用/押金/限制；全程审计时间线 |
| 泳客在泳道抽筋：发现时间/救援方式/上岸处理/联系家属/建议就医 | 救生员「抽筋救援」登记（`server/cramp.ts`），自动泳道临停+抽筋事件立案；字段完整入库并进入本场复盘 |
| 救援记录影响本场复盘与救生员站位调整 | 救援卡片记录站位调整；运营「救援复盘培训」三确认齐备后组织复盘，生成培训项并可进入排班；指挥台时间线串联全过程 |
| 救援结束：换岗、泳道临停、水面秩序恢复都要确认 | 三项收尾确认门禁（缺一不能复盘）；换岗确认真实联动 `guardDuties`（接班人自动上同一站位、占岗拒绝、不可重复）；泳道确认解除临停恢复预约/放行 |
| 站位调整后下一场巡查提醒重点关注同一泳道 | 每次调整按**版本**同步到所有未开始场次：提醒恒显最新策略，已确认遇新版重新待确认，历次策略与确认在 `history` 留痕；不回写早于事发/进行中/已结束场次；救生看板顶部提醒并须确认 |
| 复盘结果进入救生员培训和排班 | `GuardTrainingItem` 按救生员/全体派发，救生员登记参训完成，排班带教备注随培训项留存 |

## 目录结构

```

e2e-check.mjs              51 项端到端业务断言（不打进镜像）

## 主要 HTTP 接口（均在 `/api` 下，Bearer Token）

`POST /auth/login` · `GET /state`（全量实时状态，前端轮询） · `POST /bookings` · `POST /bookings/:id/checkin` · `POST /water` · `POST /issues` · `POST /incidents` 及 `/action`、`/tasks/:tid/done`、`/resolve` · `POST /pool-status`（限流/闭池/恢复联动） · `POST /tasks`、`/tasks/:id/claim|done` · `POST /guards`、`/guards/:id/relief` · `POST /locks`、`DELETE /locks/:id` · `POST /wallet/recharge` · `POST /lessons/:id/enroll` · `POST /complaints` · **`POST /cramp-rescues`（抽筋救援登记）· `POST /cramp-rescues/:id/closure/:key`（换岗/泳道恢复/秩序恢复三确认）· `POST /cramp-rescues/:id/adjust`（站位调整并带入下一场）· `POST /sessions/:id/focus-lanes/ack`（下一场确认关注）· `POST /cramp-rescues/:id/review`（运营复盘→培训/排班）· `POST /guard-training/:id/done`（参训登记）** 等。

**机构包场冲突协调（本轮新增，均在 `/api` 下）**：`POST /rentals/preview`（申请前冲突预览）· `POST /rentals`（申请，含资质/保险/年龄/儿童陪同）· `POST /rentals/:id/qualifications`（六项资质逐项核验）· `POST /rentals/:id/coordination`（拆道/缩短/限人/增派救生/暂停非公益道/补偿券/押金）· `POST /rentals/:id/reschedule-open`（向居民逐人发起改约征询）· `POST /rentals/:id/reschedule-response`（居民同意/不同意）· `POST /rentals/:id/residents/:bid/resolve`（逐人改约/保留/退费/退费+券/压缩解消）· `POST /rentals/:id/apply-agreed`（一键落单同意者）· `POST /rentals/:id/institution-confirm`（机构确认方案与费用）· `POST /rentals/:id/approve|reject`（批准生成账单并逐道加锁 / 驳回）· `POST /rentals/:id/start` · `POST /rentals/:id/gates/:key`（名单/身份/保险/救生站位/保洁/维修六岗）· `POST /rentals/:id/violations`（违规暂停、立案、扣信用）· `POST /rentals/:id/violations/:vid/resolve`（整改恢复）· `POST /rentals/:id/end` · `POST /rentals/:id/clearance/:key`（清场/清柜/复测/复位/巡查五项门禁）· `POST /rentals/:id/complete`（五项齐备恢复居民预约、释放锁区）· `POST /institutions/:id/restriction`（信用限制/增派救生/押金）· `POST /bills/:id/deduct-deposit`（押金扣抵）· `GET /rentals/:id`（按角色裁剪）。
